# todoApp-next Issue Discovery

todoApp-next のプロダクト課題を調査し、実装せずに Issue 候補として整理する。

## スコープ

このスキルで行うこと:

- バグ候補、仕様不足、機能改善、UI/UX改善、a11y課題、テスト不足を検知する
- コード、画面、テスト、既存ドキュメントから根拠を集める
- 各課題を GitHub Issue として起票できる粒度に分解する
- 優先度、影響範囲、再現手順、受け入れ条件を整理する

このスキルで行わないこと:

- コード変更
- テスト追加・修正
- `npm run lint -- --fix` などの自動修正
- コミット、push、PR作成
- 本番データや秘密情報へのアクセス

## 基本方針

- 必ず日本語で報告する。
- `.env`、APIキー、トークン、秘密鍵、証明書は読まない。
- 実装提案はしてよいが、パッチは作らない。
- 推測だけのIssueを混ぜない。根拠が弱いものは「要確認」と明記する。
- 課題は1 Issue 1論点に分ける。大きすぎる課題は分割案を出す。
- UI課題は、可能ならブラウザ確認やスクリーンショット確認で根拠を取る。
- 同じ調査コマンドが2回続けて失敗したら、原因・ログ・代替手段を整理し、別アプローチに切り替える。

## 実行方式（サブエージェント委譲）

このスキルの調査はサブエージェント経由で実行する。理由は、読み取り専用で副作用がなく、広範なファイル走査でコンテキストを大量消費する一方、成果物がIssue候補の要約に集約されるため。

- 調査本体（コード走査、grep、`npm run test:run`/`build`等の読み取り専用検証）は `Task` でサブエージェントに委譲する。
- `mixed` の場合は、調査モード（`bug-hunt`/`feature-gap`/`test-gap`）ごとにサブエージェントを分けて並列実行し、結果をマージしてIssue候補化する。各モードは独立しており同一ファイルを編集しないため衝突しない。
- 観点別の深掘りは専門エージェントに振ってよい（例: a11y → `accessibility-reviewer`、セキュリティ → `security-reviewer`、コード品質 → `code-quality-reviewer`）。汎用探索は `Explore` を使う。
- サブエージェントには「コード変更・commit・PR・自動修正は禁止。Issue候補の根拠（ファイルパス・行番号・実行結果）付きで要約のみ返す」ことを明示して渡す。

例外: `ui-ux-audit` で開発サーバー起動やブラウザ/スクリーンショット確認が必要な部分は、対話的でユーザー確認を挟むためメインセッションで実施する。コードから静的に判別できるUI/a11y課題はサブエージェントで調査してよい。

## 調査入口

ユーザー入力から調査モードを決める。

- `bug-hunt`: バグ候補を探す
- `feature-gap`: 機能不足や仕様の抜けを探す
- `ui-ux-audit`: UI/UX/a11y改善点を探す
- `test-gap`: テスト不足やリグレッションリスクを探す
- `mixed`: 上記を横断してIssue候補を出す

指定がない場合は `mixed` として進める。

## 調査手順

1. 作業ツリー確認
   - `git status --short` を実行し、既存変更を把握する。
   - 未コミット変更はユーザー作業として扱い、戻さない。

2. ルール確認
   - 共通: `.claude/rules/development.md`, `.claude/rules/code-quality.md`, `.claude/rules/security.md`
   - `app/**` 調査時: `.claude/rules/app.md`
   - `features/**` 調査時: `.claude/rules/features.md`
   - テスト調査時: `.claude/rules/testing.md`

3. コード構造把握
   - `rg --files app features tests` を優先する。
   - 画面調査は `app/**/page.tsx` から `features/**/templates`、components、hooks、contexts へ辿る。
   - API調査は `app/api/**/route.ts`、validation関連ファイル、Firebase Admin SDK利用箇所、テストを確認する。
   - 状態管理は React Context、SWR初期取得、楽観的更新、サーバーレスポンス待ちの使い分けを見る。

4. 検知観点
   - バグ: エラー処理漏れ、ロールバック漏れ、境界値、非同期競合、ユーザー切替、権限、APIレスポンス不整合
   - 機能不足: 空状態、ローディング、エラー再試行、入力制約、検索/絞り込み、管理画面の操作導線
   - UI/UX: レスポンシブ崩れ、ラベル不足、操作対象の小ささ、フィードバック不足、状態が見分けにくい表示
   - a11y: 判別不能なボタン、label不足、aria属性不足、フォーカス不可視、キーボード操作不能
   - テスト: 重要分岐の未テスト、失敗系の未テスト、Context/API/コンポーネント境界の不足

5. 必要な検証
   - 実行してもコードが変わらないコマンドだけ使う。
   - 例: `npm run test:run`, `npm run build`, `npm run test:e2e`。
   - 自動修正を伴う `npm run lint` は、このプロジェクトでは修正が入る可能性があるため、事前に package script を確認し、修正が入るなら実行しない（代わりに `--fix` なしのコマンドや `npx eslint .` などを直接実行して検証する）。
   - UI確認が必要なら開発サーバーを起動し、ブラウザで対象画面を確認する。起動が重い場合はユーザーに確認する。

## Issue候補の出力形式

Issue候補は以下の形式で出す。

```markdown
## Issue候補

### 1. [bug|feature|ui|a11y|test|security] タイトル

- 優先度: P0|P1|P2|P3
- 影響範囲: 対象画面/API/コンポーネント
- 根拠: ファイルパス、行番号、実行結果、画面確認結果
- 現状: 今どうなっているか
- 期待: どうあるべきか
- 再現手順: バグの場合のみ。未確認なら「要確認」
- 受け入れ条件:
  - 条件1
  - 条件2
- 実装メモ: 実装時に見るべきファイルや注意点。コード変更はしない
```

## 優先度基準

- `P0`: データ消失、認証/権限、主要導線の完全停止、セキュリティ影響
- `P1`: 主要機能の失敗、頻発するUX破綻、重要画面のアクセシビリティ阻害
- `P2`: 回避可能な不具合、目立つUI/UX改善、テスト不足による中程度リスク
- `P3`: 軽微な改善、文言、低頻度ケース、将来の保守性改善

## 完了報告

最後に以下を短くまとめる。

- 調査範囲
- 見つけたIssue候補数と内訳
- 最優先で起票すべきIssue
- 根拠が弱く追加確認が必要な項目
- 実装には進んでいないこと
