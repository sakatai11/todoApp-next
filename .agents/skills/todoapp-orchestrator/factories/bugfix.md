# Factory: bugfix（設計フェーズ）

バグ修正のための **設計工場**。Phase 3a で起動され、根本原因を特定して **Codex に渡す実装指示書を出力する**。**修正コードやテストの実装は行わない**（実装は Phase 3b の Codex）。ただし bugfix では **再現テスト先行（red → green）** をリグレッション防止の中核とするため、その手順を指示書に明記する。

## 入力

`NormalizedTask`（type=bugfix または type=optimization）

- `type=bugfix`: `context.reproSteps` が必須（trigger 段階で確保済み）
- `type=optimization`: 計測指標（PostHog/Lighthouse 等）が `description` に明記されていること。「再現テスト」は「ベースライン計測の記録」に読み替え、指示書には「修正後に数値改善（例: LCP -Xms、バンドル -XKB）を確認させる」旨を書く

## ゴール

`phases/phase3-factory-execution.md` の「実装指示書テンプレート」に沿った Markdown 本文を返す。

## 処理フロー

### Step 1: 原因調査

`code-explorer` エージェントを起動して根本原因を特定する：

```
プロンプト:
「以下の再現手順で発生するバグの根本原因を特定してください。

# 再現手順
<reproSteps>

# 期待動作
<description から抽出>

# 実際の動作 / エラー
<description から抽出>

該当する以下のファイルを特定してください:
1. 直接の発生源
2. 関連する状態管理（Context / SWR）
3. 関連するAPI（あれば）
4. 関連するテスト

修正前の現状を正確にトレースしてください。」
```

### Step 2: 既存テストの確認

```bash
grep -r "<関連する関数名>" tests/ --include="*.test.ts" --include="*.test.tsx"
```

既存テストがあるか、ない場合はどこに追加するかを判断し、指示書セクション2/5 に反映する。

### Step 3: 実装指示書の生成

特定した根本原因をもとに、指示書テンプレートを埋める。bugfix 固有として以下を必ず指示書に含める：

- **セクション5（テスト要件）に red→green の手順を明記**:
  - 修正コードより**先に**再現テストを書かせる（例: `features/todo/contexts/__tests__/TodoContext.test.tsx` に `describe('Bug: <title>')`）
  - `npm run test:run -- <該当ファイル>` で **red を確認** → 修正 → **green を確認** → 関連ディレクトリの回帰確認
- **セクション3（方針）**: Step 1 で特定した根本原因と修正箇所
- **セクション6（禁止事項）**: バグ修正に直接関係ないリファクタはしない、修正は最小スコープ、既存パターン（楽観的更新/サーバー待ち）を踏襲

### Step 4: 返却

完成した実装指示書本文（Markdown）だけを返す。

→ orchestrator が `.codex-tasks/<branchSlug>.md` に書き出し、指示書承認ゲート（Phase 3a）→ Phase 3b（Codex 実装）へ。

## 想定外パターン（設計段階で検出したら指示書化せず人間へ）

### バグが再現できない

- 環境依存（特定のブラウザ / OS / データ状態）の可能性
- 人間に質問: 「再現環境の詳細を教えてください（ブラウザ / OS / ユーザーデータ）」
- 再現できなければパイプライン中断、調査タスクに切り替え（Codex には渡さない）

### 修正が広範囲に及ぶ

- 1ファイル / 数百行に収まらない場合は人間に確認
- 「これは bugfix の範囲を超えるリファクタリングが必要です。続行しますか？」

### 既存テストも修正必要

- バグ修正で既存テストが意図的に red になる場合、そのテストが「バグを正しい仕様として固定していた」可能性
- 人間に確認: 「以下の既存テストも修正が必要です。これは仕様変更扱いになります」。承認が取れたら、その旨を指示書セクション5/6 に明記して Codex に渡す
