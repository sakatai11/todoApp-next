# Factory: feature（設計フェーズ）

新機能のための **設計工場**。Phase 3a で起動され、探索とアーキテクチャ設計を行い、**Codex に渡す実装指示書（`.codex-tasks/<branchSlug>.md` の本文）を出力する**ことをゴールとする。**実装・テスト作成・コミットは行わない**（実装は Phase 3b の Codex が指示書に基づいて行う）。

## 入力

`NormalizedTask`（type=feature）

## ゴール

`phases/phase3-factory-execution.md` の「実装指示書テンプレート」に沿った Markdown 本文を返す。

## 処理フロー

### Step 1: Codebase Exploration

`code-explorer` エージェントを 2〜3 並列で起動する。各エージェントは：

- コードを包括的にトレースし、抽象化・アーキテクチャ・制御フローを深く理解する
- コードベースの異なる側面をターゲットにする
- 読むべき重要ファイル 5〜10 個のリストを返す

**エージェントプロンプト例**:

- 「`<NormalizedTask.title>` に類似した機能を探して実装を包括的にトレースしてください」
- 「`<NormalizedTask の関連エリア>` のアーキテクチャと抽象化をマッピングしてください」
- 「`<context.relatedDocs>` に記載された仕様書を読み、実装に必要なコンテキストを収集してください」

**このプロジェクト固有の観点**:

- `features/` のフィーチャーベース設計パターンを確認
- `features/shared/` の共通コンポーネント活用可否を確認
- React Context + SWR の状態管理パターンとの整合性を確認
- 楽観的更新 vs サーバーレスポンス待ちパターンの使い分けを確認

エージェント完了後、返却されたファイルを全て読んで深い理解を構築する。

### Step 2: Architecture Design（アーキ選択ゲート）

`code-architect` エージェントを 2〜3 並列で起動する（異なるフォーカス）：

- **最小変更**: 最小限の変更で最大限の既存コード再利用
- **クリーンアーキテクチャ**: 保守性と優れた抽象化を重視
- **プラグマティックバランス**: 速度と品質のバランス

全アプローチをレビューし、ユーザーに提示する：

- 各アプローチの概要とトレードオフ比較
- **推奨案と理由**
- 具体的な実装の違い

**どのアプローチを希望するかユーザーに確認する**（これがアーキ選択ゲート。指示書承認ゲートの前に行う）。

### Step 3: 実装指示書の生成

選択されたアーキテクチャをもとに、`phase3-factory-execution.md` のテンプレート（セクション1〜8）を埋めた実装指示書本文を作成する。特に：

- **セクション2（変更/作成対象ファイル）**: Step 1 で特定したファイルを確定リスト化（パス + 変更1行）
- **セクション3（アーキ方針と理由）**: Step 2 で選択したアプローチと「なぜ」
- **セクション4（遵守規約）**: フィーチャーベース設計、MUI+Tailwind、新規 API の Zod 必須、楽観的更新/サーバー待ちの使い分け、タスク固有の禁止ルール
- **セクション5（テスト要件）**: 各対象ファイルに対応する UT を実装と同時に作成させる

> 大規模（新規3ファイル以上 / 複数 features 横断 / API+FE 両方）の場合、セクション2の実装順序も明記しておくと Codex が迷わない。`EnterPlanMode` は使わない（指示書がその役割を兼ねる）。

### Step 4: 返却

完成した実装指示書本文（Markdown）だけを返す。探索ログ・コードの引用は含めない。

→ orchestrator が `.codex-tasks/<branchSlug>.md` に書き出し、指示書承認ゲート（Phase 3a）→ Phase 3b（Codex 実装）へ。
