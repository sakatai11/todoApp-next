# Feature Development（todoApp-next専用）

グローバルの `feature-dev` をベースに、Phase 6 のコードレビューをこのプロジェクトの専門エージェント群（`code-review` オーケストレーター）に差し替えたバージョン。

## Core Principles

- **Ask clarifying questions**: 曖昧な点・エッジケース・未定義の挙動を全て特定する。仮定を立てず具体的な質問をする。コードベース理解後、アーキテクチャ設計前に質問する。
- **Understand before acting**: 既存コードパターンを先に読んで理解する
- **Read files identified by agents**: エージェント起動後、返却された重要ファイルリストを読んで詳細なコンテキストを構築する
- **Simple and elegant**: 読みやすく・保守性が高く・アーキテクチャ的に健全なコードを優先
- **Use TodoWrite**: 全フェーズの進捗をトラッキングする

---

## Phase 1: Discovery

**Goal**: 何を作るかを理解する

Initial request: $ARGUMENTS

**Actions**:

1. 全フェーズのTodoリストを作成
2. 機能が不明な場合、ユーザーに確認：
   - 解決しようとしている問題は何か？
   - 機能は何をすべきか？
   - 制約や要件はあるか？
3. 理解内容を要約してユーザーと確認

---

## Phase 2: Codebase Exploration

**Goal**: 関連する既存コードとパターンを高レベル・低レベルの両面で理解する

**Actions**:

1. `code-explorer` エージェントを2〜3並列で起動する。各エージェントは：
   - コードを包括的にトレースし、抽象化・アーキテクチャ・制御フローを深く理解する
   - コードベースの異なる側面をターゲットにする（類似機能・高レベル理解・アーキテクチャ・UX等）
   - 読むべき重要ファイル5〜10個のリストを返す

   **エージェントプロンプト例**:
   - 「[機能]に類似した機能を探して実装を包括的にトレースしてください」
   - 「[機能エリア]のアーキテクチャと抽象化をマッピングし、コードを包括的にトレースしてください」
   - 「[既存機能/エリア]の現在の実装を分析し、包括的にトレースしてください」
   - 「[機能]に関連するUIパターン・テストアプローチ・拡張ポイントを特定してください」

   **このプロジェクト固有の観点**:
   - `features/` のフィーチャーベース設計パターンを確認
   - `features/shared/` の共通コンポーネント活用可否を確認
   - React Context + SWR の状態管理パターンとの整合性を確認
   - 楽観的更新 vs サーバーレスポンス待ちパターンの使い分けを確認

2. エージェント完了後、返却されたファイルを全て読んで深い理解を構築する
3. 発見したパターンと知見の包括的なサマリーを提示する

---

## Phase 3: Clarifying Questions

**Goal**: 設計前に全ての曖昧な点を解消する

**CRITICAL**: 最も重要なフェーズの1つ。スキップ不可。

**Actions**:

1. コードベースの知見と元の機能要求をレビューする
2. 未定義の側面を特定：エッジケース・エラーハンドリング・統合ポイント・スコープ境界・設計の好み・後方互換性・パフォーマンス要件
3. **明確に整理されたリストでユーザーに全質問を提示する**
4. **回答を待ってからアーキテクチャ設計へ進む**

ユーザーが「あなたの判断で」と言った場合は、推奨案を提示して明示的な確認を取る。

---

## Phase 4: Architecture Design

**Goal**: トレードオフが異なる複数の実装アプローチを設計する

**Actions**:

1. `code-architect` エージェントを2〜3並列で起動する（異なるフォーカス）：
   - **最小変更**: 最小限の変更で最大限の既存コード再利用
   - **クリーンアーキテクチャ**: 保守性と優れた抽象化を重視
   - **プラグマティックバランス**: 速度と品質のバランス
2. 全アプローチをレビューし、このタスクに最適なものについて意見を形成する（小修正か大機能か・緊急度・複雑さ・チームコンテキストを考慮）
3. ユーザーに提示する：各アプローチの概要・トレードオフ比較・**推奨案と理由**・具体的な実装の違い
4. **どのアプローチを希望するかユーザーに確認する**

---

## Phase 5: Implementation

**Goal**: 機能を実装する

**ユーザーの承認なしに開始しないこと**

**Actions**:

1. ユーザーの明示的な承認を待つ
2. 前フェーズで特定された関連ファイルを全て読む
3. 選択されたアーキテクチャに従って実装する
4. コードベースの規約を厳密に遵守する：
   - フィーチャーベース設計（`features/`で自己完結）
   - MUI + Tailwind CSS パターン
   - Zodバリデーション（新規APIに必須）
   - 楽観的更新 or サーバーレスポンス待ちの適切な使い分け
5. Todoを更新しながら進める

---

## Phase 6: Quality Review（プロジェクト専用オーケストレーター使用）

**Goal**: コードの品質・セキュリティ・パフォーマンス・アクセシビリティを総合的に検証する

> **このフェーズはグローバル版 `feature-dev` と異なります。**
> 汎用の `code-reviewer` × 3 ではなく、このプロジェクトの `code-review` オーケストレーターを使用します。

**Actions**:

1. `code-review` スキルを起動する（Skill ツールで `skill: "code-review"` を実行）
   - `code-review` は変更ファイルのパターンに応じて以下の専門エージェントを自動選択・並列起動する：

     | エージェント                | 起動条件                     |
     | --------------------------- | ---------------------------- |
     | `code-quality-reviewer`     | 常時                         |
     | `security-reviewer`         | API・認証ファイル変更時      |
     | `api-design-reviewer`       | `app/api/**` 変更時          |
     | `performance-reviewer`      | コンポーネント・フック変更時 |
     | `accessibility-reviewer`    | UIコンポーネント変更時       |
     | `frontend-pattern-reviewer` | フロントエンドファイル変更時 |

   - CodeRabbit（静的解析）+ Codex（他社レビュー）も自動実行される

2. `code-review` の集約レポートを受け取る

3. **Critical / High の問題をユーザーに提示し、どうするか確認する**（今すぐ修正・後で修正・そのまま進む）

4. ユーザーの判断に基づいて問題に対処する

---

## Phase 7: Summary

**Goal**: 達成内容をドキュメント化する

**Actions**:

1. 全Todoを完了としてマーク
2. 以下をサマリーとして提示：
   - 何を作ったか
   - 主要な決定事項
   - 変更したファイル
   - 推奨する次のステップ
